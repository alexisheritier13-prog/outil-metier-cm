# Story 1.2: Mise en place de Supabase et des migrations

## Status

Review — code complet, **vérification contre une instance Supabase en attente** (Docker
absent sur la machine ; nécessite `supabase start` ou un projet cloud).

## Story

**As a** développeur,
**I want** un projet Supabase relié au dépôt avec des migrations SQL versionnées,
**so that** le schéma de base est reproductible et évolue de façon contrôlée.

## Acceptance Criteria

1: Le dépôt contient un dossier `supabase/` avec la config CLI et un dossier `migrations/`.
2: Une première migration crée une table `app_meta` (ou équivalent) et active les extensions nécessaires (`pg_cron`, `pg_net`, `pgcrypto`).
3: Le client Supabase est configuré dans l'app via des variables d'environnement (URL, clé anon), jamais de clé service côté client.
4: La procédure d'application des migrations (local + CI/prod via `supabase db push`) est documentée.
5: Un test d'intégration de base se connecte à une instance Supabase locale et lit `app_meta`.

## Dev Notes

### Contexte

Story 1.1 a livré la base Vite/React/TS. Ici on ajoute la couche Supabase **sans** pouvoir
la faire tourner : Docker n'est pas installé sur la machine de dev, donc `supabase start`
est indisponible. Tout le code est écrit et les tests unitaires passent ; la validation
contre une vraie base se fera quand Docker sera installé ou qu'un projet cloud existera.

### Décisions

- **`pg_cron` / `pg_net` reportées à l'Epic 8** : elles ne sont pas activables de façon
  fiable sur toutes les instances locales et ne servent qu'à l'ordonnancement des jobs
  (Epic 8). `0001_init.sql` n'active que `pgcrypto`, `citext`, `pg_trgm` (sûres partout).
  L'AC 2 cite `pg_cron`/`pg_net` « si nécessaire » — elles ne le sont pas à ce stade.
- **`app_meta`** : table clé/valeur `jsonb`, RLS `select` pour `anon`/`authenticated`,
  aucune policy d'écriture (seul `service_role` écrit, il contourne la RLS). Sert de cible
  triviale au test de connexion et portera plus tard des flags applicatifs.
- **Client Supabase lazy** : `getSupabase()` ne crée le client qu'au premier appel, pour
  que l'app (page canari, tests) fonctionne sans `.env.local`. `requireSupabaseEnv()` lève
  une erreur explicite listant les variables manquantes.
- **`config.toml`** : `db.major_version = 17` (défaut CLI courant). L'archi mentionnait
  Postgres 15 ; 17 est compatible et sera la version du projet — à répercuter dans
  `docs/architecture/tech-stack.md` si besoin. Le projet cloud devra être créé en 17
  (ou le `major_version` ajusté à la version cloud choisie).

### Standards applicables (`docs/architecture/coding-standards.md`)

- Accès Supabase uniquement via `src/services/` — respecté (`appMeta.ts`).
- Aucun secret côté client — seules `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`.
- `database.ts` régénéré après chaque migration, jamais édité à la main (ici : stub
  temporaire clairement signalé).
- Toute migration touchant une policy ajoute un test dans `tests/` — fait (test
  d'intégration `app_meta`, en attendant pgTAP à l'arrivée des vraies tables en 1.3).

### Procédure migrations (résumé, détaillée dans le README)

- **Local** (Docker requis) : `supabase start` puis `supabase db reset` (applique
  `migrations/` + `seed.sql`).
- **Prod / cloud** : `supabase link --project-ref <ref>` puis `supabase db push` — exécuté
  par le workflow `.github/workflows/db-migrate.yaml` sur `main` (déjà présent depuis 1.1,
  activé quand les secrets `SUPABASE_*` seront renseignés).

### Testing

- **Unitaire** (Vitest, tourne partout) : `src/lib/env.test.ts`.
- **Intégration DB** : `tests/integration/*.integration.test.ts` — `describe.skip`
  automatique si `SUPABASE_TEST_URL` / `SUPABASE_TEST_ANON_KEY` absents. Lancement documenté
  dans `tests/integration/README.md`.
- **RLS (pgTAP)** : arrivera en Story 1.3 avec les premières vraies tables (`profiles`,
  `clients`, `user_clients`).
