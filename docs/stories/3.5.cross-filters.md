# Story 3.5: Filtres et recherche transverses

## Status

Done — `FiltersBar` + hook `useFilters` (URL source de vérité + miroir localStorage),
appliqués aux 4 vues. 6 tests unitaires + 3 intégration verts.

## Story

**As a** CM,
**I want** filtrer et chercher les posts par client, statut, réseau, période et mot-clé,
**so that** je retrouve rapidement les posts pertinents dans toutes les vues.

## Acceptance Criteria

1: Barre de filtres persistante : client (multi), statut (multi), réseau (multi), période (plage de dates), tag (multi), recherche plein texte sur la légende.
2: Les filtres s'appliquent identiquement aux vues Mois/Semaine/Liste/Kanban.
3: L'état des filtres est mémorisé par utilisateur (persisté) et reflété dans l'URL (partageable).
4: La recherche plein texte utilise un index Postgres (`tsvector` ou `pg_trgm`) ; temps de réponse < 500 ms sur le jeu de test.
5: Tests d'intégration sur la combinaison de filtres et l'isolation (un `cm` ne filtre que sur ses clients).

## Dev Notes

### Décisions

- **URL = source de vérité** (pas Zustand). Filtres partageables (AC 3) et l'historique du
  navigateur fonctionne. `localStorage` n'est qu'un miroir « dernière config » restauré à
  l'arrivée sur une URL nue. **Zustand toujours pas installé** — sera ajouté quand un état
  UI non-URL en aura vraiment besoin (sélection multiple, Story 9.1).
- **Tags** (AC 1) : absent — la table `tags` arrive en Story 3.6. `useFilters` ajoutera une
  clé `tag` à ce moment-là.
- **Période en jours Paris** : `from`/`to` sont des dates (`YYYY-MM-DD`) ; `toService` les
  convertit en `00:00`/`23:59` heure de Paris → UTC (cohérent avec le stockage des posts).
- **`setSp(..., { replace: true })`** : les changements de filtre ne polluent pas
  l'historique de navigation (un seul « retour » quitte la page).
- **Perf recherche** : index GIN `posts_search_idx` (0008) + `websearch` FR. Non mesuré
  automatiquement ; le jeu de données de test est petit.
