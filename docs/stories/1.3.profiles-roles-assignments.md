## Story

**As a** Admin agence,
**I want** que chaque compte ait un rôle et, pour les internes, une liste de clients assignés,
**so that** l'outil peut restreindre l'accès selon le rôle et le périmètre.

## Acceptance Criteria

1: Migration créant `profiles` (id = `auth.users.id`, nom, email, `role` parmi `cm|lead|admin|client`, `is_active` booléen, timestamps).
2: Migration créant `clients` (minimal : id, nom, `is_archived`, timestamps) — suffisant pour les assignations, enrichi en Epic 2.
3: Migration créant `user_clients` (profile_id, client_id, unique) pour les assignations des rôles internes.
4: Un trigger crée automatiquement une ligne `profiles` à l'inscription d'un `auth.users`, avec `role` par défaut `cm` et `is_active = false`.
5: RLS activé sur les trois tables ; une fonction SQL `auth_role()` et `has_client_access(client_id)` sont définies et testées.
6: Tests d'intégration : un `cm` ne lit que les `clients` présents dans ses `user_clients` ; un `lead`/`admin` lit tous les `clients` non supprimés.

## Dev Notes

### Décisions

- **`current_role()` → `auth_role()`** : `current_role` est un mot réservé PostgreSQL.
  L'archi utilise déjà `auth_role()`.
- **`profiles` lecture** : self + admin uniquement en 1.3. Lead/CM n'ont pas besoin de lire
  les profils des autres à ce stade (viendra si un écran d'équipe l'exige, Story 1.5).
- **`profiles` update self** : autorisé pour le `full_name` seulement — la policy
  `with check` fige `role` et `is_active` à leur valeur courante (un utilisateur ne peut ni
  s'auto-promouvoir ni s'auto-activer).
- **`handle_new_user` `security definer`** : le trigger sur `auth.users` doit écrire dans
  `public.profiles` ; `on conflict do nothing` pour l'idempotence.
- **`clients` créée ici avec ses colonnes Epic 2** (`logo_url`, `sector`, `archived_at`,
  `deleted_at`, `deleted_by`) pour éviter une migration d'altération immédiate en 2.1 ; la
  logique/UI d'archivage et de corbeille reste pour l'Epic 2 / Story 3.7.
