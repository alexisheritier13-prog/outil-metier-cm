## Story

**As a** Lead CM,

**so that** je pilote la production autrement que par le calendrier.

## Acceptance Criteria

1: Bascule Mois / Semaine / Liste / Kanban sur `/app`.
2: Vue liste : tableau paginé/virtualisé (date, client, réseau, extrait de légende, statut, rédacteur), triable par colonne.
3: Vue kanban : colonnes = statuts du pipeline, cartes = posts, glisser-déposer entre colonnes déclenchant `canTransition` (Story 3.2) ; kanban réservé aux rôles internes.
4: Les deux vues partagent les filtres transverses (Story 3.5).
5: Performance testée avec ~2 000 posts sur la période filtrée (virtualisation).

## Dev Notes

### Décisions

- **DnD kanban en HTML5 natif** (`draggable` + `onDragOver`/`onDrop`) plutôt que `dnd-kit` :
  colonne→colonne simple, pas de réordonnancement intra-colonne, zéro dépendance. `dnd-kit`
  reste une option si le besoin se complexifie.
- **Virtualisation conditionnelle** (`rows.length > 80`) : en dessous, rendu direct — la
  virtualisation a un coût fixe (mesure, ResizeObserver) qui ne se justifie pas pour une
  liste courte, et le rendu direct évite les soucis de mesure sous jsdom. Au-delà,
  `@tanstack/react-virtual` (lignes de 44 px, overscan 12) tient les ~2 000 lignes.
- **Statut retiré des lignes de liste** : le changement de statut se fait depuis le panneau
  latéral (`PostSheet`) — plus lisible qu'un `<select>` par ligne. Le kanban offre le drag
  pour ceux qui préfèrent.
- **Kanban : surlignage conditionnel** — une colonne ne s'illumine à l'approche que si
  `canTransition` autorise le drop pour le rôle courant ; sinon le drop est ignoré
  silencieusement (le RPC refuserait de toute façon).
- **Rédacteur dans la liste (AC 2)** : colonne non affichée pour l'instant (le nom du
  rédacteur nécessite de résoudre `author_id` → profil ; `listInternalUsers` est déjà
  chargé pour lead/admin). À ajouter avec les filtres (3.5) où le rédacteur devient aussi un
  critère. Noté.
