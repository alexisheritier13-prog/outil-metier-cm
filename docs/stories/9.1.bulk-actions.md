# Story 9.1 : Sélection multiple et actions en masse

## Status

Done — cases à cocher dans les vues Liste et Kanban, barre d'actions flottante
(dupliquer / statut / réassigner / corbeille), exécution atomique par post avec
récapitulatif des échecs. 16 tests unitaires + 3 tests d'intégration.

## Story

As a CM,
I want sélectionner plusieurs posts et agir sur eux d'un coup,
so that je traite les opérations répétitives rapidement.

## Acceptance Criteria

1. Sélection multiple dans les vues Liste et Kanban (cases à cocher, « tout
   sélectionner » sur le résultat filtré) ; barre d'actions flottante. ✅
2. Actions : dupliquer, changer de statut (soumis à `canTransition` pour chaque
   post, rapport des échecs), mettre en corbeille (règles FR45), réassigner à un
   autre CM (Lead/Admin). ✅
3. Chaque action en masse est atomique par post et produit un récapitulatif
   (« 12 réussies, 2 refusées : … »). ✅
4. Chaque modification unitaire est journalisée normalement (Story 4.4) — les
   actions passent par les RPC / UPDATE existants, donc les triggers
   `posts_log_*` s'appliquent. ✅
5. Tests d'intégration sur les cas partiels (certains posts hors droits). ✅

## Dev Notes

### Décisions

- **Exécution côté client, pas de RPC « batch ».** Chaque action réutilise le
  chemin unitaire déjà sécurisé (`post_change_status`, `post_trash`,
  `post_duplicate`, UPDATE `author_id`). La boucle applicative itère, capture les
  échecs et produit le récap. Pas de nouvelle migration : le serveur reste
  l'autorité (RLS + `can_transition`), le client ne fait qu'agréger.
- **Atomicité par post = grain naturel.** Un échec (droits, transition
  impossible, commentaire manquant) n'interrompt pas la boucle ; il est listé
  dans le récapitulatif avec un libellé lisible (`Client · extrait de légende`).
- **Changement de statut :** les posts déjà dans le statut cible ou dont la
  transition n'est pas permise pour le rôle sont écartés *avant* l'appel réseau
  (`partitionByTransition`) et comptés comme refus a priori. Si au moins une
  transition retenue exige un commentaire, un seul commentaire est demandé et
  appliqué à toutes.
- **Réassignation réservée Lead/Admin** dans l'UI (cohérent avec `PostForm`), la
  RLS l'autoriserait à tout interne ayant accès au client.
- **Sélection non persistée** : elle vit dans `PlanningPage` et se vide dès que le
  résultat filtré change (les ids affichés ne sont plus les mêmes).
